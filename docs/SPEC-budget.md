# SPEC-budget：旅行预算与费用完整性

> 版本：v0.1｜状态：已批准｜批准日期：2026-10-27（北京时间）  
> 对应已批准模块：Capability Map `budget`；本规格已获批准，可进入计划阶段。规格批准不等于任务、实现、持久化或真实数据能力获批。

## 0. 草案假设与边界提示

1. 本规格将 `budget` 作为 P0 核心切片中的纯预算领域能力：按唯一费用项汇总总预算、已支付、待支付估算、预留金和完整性；不拥有住宿、交通、活动等事实来源。
2. 费用金额沿用 foundation 的整数分和 `CNY`；`null` 是未知／未补齐，`0` 是用户或来源明确确认的零。
3. 本模块按输入的单次预算快照计算，不自行持久化账号、游客、行程或费用记录。IndexedDB 与身份分区属于 `local-storage`／`auth` 后续模块；本 SPEC 不提前引入它们。
4. 预订锁定和解锁由 `itinerary` 负责。预算可以保留费用项与预订的稳定关联并报告金额，不得自行解锁或改写锁定预订。
5. 首版金额／人数／费用项数量等产品上下限未确认（Q-006）；草案不设置未经批准的业务上限。运行时安全资源限制须在计划阶段提出、验证且不得伪装为产品限制。

## 2. Objective 与范围

### 目标

让用户能判断一趟单城市行程的预算使用情况，且每个合计可以追溯到唯一费用项。用户必须能区分：总预算、已支付、待支付估算、剩余可安排、预留金、预计结余和超支；缺价、来源不完整或费用未核实时，不把预算结果伪装成确定结论。

### 首版包含

- 一份单城市旅行预算快照：总预算可未设置；货币固定 `CNY`。
- 费用项的唯一 `cost_id`、费用类别、可选预订关联、已支付金额、预计未支付金额、来源／证据状态和完整性状态。
- 汇总总预算、已支付、待支付已知合计、剩余可安排金额和预计结余／最低已知超支。
- 用户手动设置或清除预留金；预留金不自动生成。总预算达到或超过 300,000 分且尚未设置预留金时，仅显示非强制提醒。
- 手工费用输入与报价事实分离；对未接入的住宿／机票报价，允许 D-016 所述的用户填写金额，并始终标为“用户填写，非平台报价”。
- 费用覆盖不完整或金额未知时显示“待核实”；已知金额已经超预算时可显示“至少超出”金额。
- 纯计算服务／契约及响应式预算摘要和编辑交互；用户确认、保存动作和预算快照边界清晰。

### 首版不包含

- 供应商搜索、酒店房价、机票／铁路票价、路线、门票、活动或天气事实的采集与验证。
- 站内预订、支付、退款、银行卡／支付账户、自动购买或供应商付费回退。
- 自动创建预留金、按比例推荐预留金、自动调低预算或裁定“适合旅行”。
- 费用重复导入识别和自动合并；`imports` 拥有文件哈希／候选匹配，budget 只接受已确认的唯一费用项。
- 预订锁定、解锁、改期或更改已确认的外部预订金额；锁定规则由 `itinerary` 执行。
- 服务器端账户／行程／费用持久化、IndexedDB 分区、跨设备同步、公共分享链接和 PDF 打印；分别由 auth/local-storage/exports 后续规格定义。
- 未经批准的金额、费用数量、行程人数或天数上下限。

## 3. 输入输出契约

### 输入

| 字段／对象 | 类型 | 必填 | 空值语义 | 校验 | 来源／权限 |
|---|---|---:|---|---|---|
| `trip_id` | 稳定字符串 ID | 是 | 不允许为空 | 字符串格式按 foundation ID 约束；同一快照中的费用必须属于同一单城市行程 | 调用方；本模块不执行身份授权 |
| `total_budget_fen` | 非负整数分或 `null` | 否 | `null` 表示用户尚未设置总预算；0 表示明确设为 0 | 拒绝负数、float、bool；不设置额外上限 | 用户设置；不能从费用反推 |
| `reserve_fen` | 非负整数分或 `null` | 否 | `null` 表示用户未设置；0 表示明确选择零预留 | 同总预算；不得根据百分比自动填入 | 用户显式设置／清除 |
| `cost_items[]` | 唯一费用项数组 | 是 | 空数组表示当前无费用项，不代表所有费用已核实为零 | `cost_id` 不重复；字段严格校验；不得重复纳入同一预订的费用 | 用户确认，或后续模块提供的已确认记录 |
| `paid_fen` | 非负整数分或 `null` | 费用项必填字段 | `null` 表示支付金额未知；0 表示确认尚未支付 | 不得默认为 0；只统计一次 | 用户输入／已核实来源 |
| `unpaid_estimate_fen` | 非负整数分或 `null` | 费用项必填字段 | `null` 表示预计未支付金额未知／未提供；0 表示确认无剩余应付 | 不与订单总价再重复相加；金额有效性和分项拆分须保持一致 | 用户输入／来源报价 |
| `reservation_id` | 可空稳定 ID | 否 | 空表示费用不是已知预订关联项 | 同一个预订只能由一个 `cost_id` 作为预算主项；多次支付拆分归在同一费用项 | itinerary/imports 边界提供；不可据此改写预订 |
| `category` | 费用类别枚举／用户分类 | 是 | 不允许空；不改变金额语义 | 首版建议类别：往返交通、住宿、餐饮、市内交通、门票、活动、其他；这些仅用于归类，不表示真实报价能力 | 用户或来源；具体选项需审阅 |
| `evidence_state` | foundation `EvidenceState` | 是 | 不允许省略 | `user_provided`、`verified`、`unverified`、`estimate`、`demo`、`unknown` 保持来源真实性语义 | 对应用户／来源；不得由 budget 升级证据等级 |
| `completeness` | `complete` / `needs_review` | 是 | 不允许空 | `needs_review` 表示金额或归属未补齐；由调用方依据必要项标记并可由服务校验 | 来源／用户确认状态 |

### 输出

| 字段／对象 | 类型 | 可空 | 语义 | 来源／时间 | 是否持久化 |
|---|---|---:|---|---|---:|
| `total_budget_fen` | 非负整数分 | 是 | 原样返回用户预算设置 | 用户输入 | 否 |
| `paid_total_fen` | 非负整数分 | 是 | 唯一费用项中所有已知已支付金额的合计；若存在无法判定的支付额则不得声称完整合计 | 对应费用项 | 否 |
| `known_unpaid_total_fen` | 非负整数分 | 是 | 当前已知的待支付金额合计；有未知项时必须伴随不完整状态，不可解释为最终待支付总额 | 对应费用项／报价 | 否 |
| `remaining_to_allocate_fen` | 整数分 | 是 | `total_budget_fen - paid_total_fen`；仅当预算和已支付合计均完整已知时提供，可为负数以表达已支付超预算 | 由输入计算 | 否 |
| `expected_balance_fen` | 整数分 | 是 | `total_budget - paid - unpaid estimate - reserve`；仅所有必要金额和费用完整且预算已设置时提供 | 由输入计算 | 否 |
| `minimum_over_budget_fen` | 非负整数分 | 是 | 缺项仍存在时，已知支出／预留金已超过预算的最小超出额；仅已知时超支成立才提供 | 由已知输入计算 | 否 |
| `budget_state` | 模块状态 | 否 | `unconfigured`、`needs_review`、`within_budget`、`over_budget`；状态规则见 §4 | 由计算结果决定 | 否 |
| `reserve_reminder` | 布尔值 | 否 | 仅在预算 ≥ 3,000 元且预留金为 `null` 时提示；不创建金额，不要求用户操作 | 由已确认 D-014 规则决定 | 否 |
| `request_id` | UUID | 否 | 通过 foundation 关联请求；错误体和响应头保持一致 | 服务端 | 仅可脱敏关联日志 |

`MoneyAmount` 使用 foundation 的 `amount_fen`／`currency_code` 语义；API 若需要多个金额单位，应保持同一响应货币 `CNY` 并禁止混合币种静默汇总。金额以整数分运算；前端元输入须通过 Decimal／字符串十进制明确转换和舍入，具体舍入策略列为计划前决策，不使用 JS 二进制浮点作为权威账值。

## 4. 状态与错误

| 状态／错误码 | 触发条件 | 用户提示 | 可重试 | 返回计算结果 |
|---|---|---|---:|---:|
| `unconfigured` | 总预算未设置且无可形成有效摘要的金额配置 | 提示先设置总预算；可显示已知费用但不显示预算内结论 | 可编辑后重算 | 部分已知汇总可返回 |
| `needs_review` | 存在未知金额、未确认费用或费用列表不完整 | 明确标记待核实；不得把 null 当零 | 用户补充／确认后重算 | 返回可确认的已知小计，不输出确定结余 |
| `within_budget` | 总预算已知，输入费用完整，计算预计结余不小于零 | 展示预算状态和计算口径 | 编辑后重算 | 是 |
| `over_budget` | 总预算已知且已知支付／待支付／预留金额超过预算 | 展示已知超出额；数据不完整时说明至少超出 | 编辑后重算 | 是；若存在未知项则只输出最低已知超支 |
| `VALIDATION_ERROR` | 负金额、重复 `cost_id`、非法状态、字段缺失或金额结构矛盾 | 指出可修正字段；不暴露后端细节 | 修正后可重试 | 否 |
| `FORBIDDEN` | 调用方请求了与当前主体无关数据（在未来加入 owner scope 后） | 通用无权限提示 | 修复主体／权限后 | 否 |
| `INTERNAL_ERROR` | 未预期错误 | 通用提示并附 request ID | 按纯计算请求可安全重试 | 否 |

上述 budget 状态为**本模块草案**，不是新增 foundation `ResultState`。不以 `live` 表示预算计算可信；费用的来源证据和计算完整度是不同维度。`needs_review` 与 `over_budget` 可同时成立，需用稳定组合字段表达，例如 `budget_state=over_budget` 且 `completeness=needs_review` 并填 `minimum_over_budget_fen`。

## 5. 权限、隐私与数据保留

- 当前 SPEC 的预算计算输入由单次请求提供；模块不落盘，不包含身份认证、owner scope 或服务端行程保存。
- 浏览器不在 URL、遥测、控制台日志或 E2E trace 中记录具体旅行费用、订单号或用户填写内容；测试使用合成金额与虚构 ID。
- API 日志只记 request ID、路由、状态和耗时；不记录费用数组、金额、订单关联值、请求体或来源查询参数。
- 仅允许响应调用方提交且通过校验的费用数据；不接受上传文件原件、OCR 全文或凭证内容作为计算输入。
- 本模块不发送模型请求，不触发外部供应商，不持有 Key。
- 将来持久化由 `local-storage`／`auth` 的独立 SPEC 定义，需按 owner 分区；本 SPEC 不允许借用全局缓存保存用户费用。
- 删除与保留策略由持久化模块负责；本模块无持久化数据和清理作业。

## 6. 业务规则与不变量

1. 总预算是整趟旅行、全体出行人员的金额，不按人均解释（D-013）。
2. 金额只用整数分；`null` 是未知／未设置，0 是明确零；不允许负数、浮点输入作为权威账值或静默四舍五入。
3. `remaining_to_allocate = total_budget - paid_total`。示例：预算 600,000 分，已付 200,000 分，剩余可安排 400,000 分。
4. 已支付金额属于总预算已使用额，不能和订单总价再次相加。同一预订只有一个费用主 ID；部分支付的预订拆为该费用项中的已支付与待支付分量（D-015）。
5. 待支付估算和预留金参与预计结余，不改变“剩余可安排”公式。预计结余示例：预算 600,000 分，已支付 200,000 分，待支付 300,000 分，用户预留 60,000 分，预计余额为 40,000 分。
6. 预留金不自动创建、不按固定比例建议。预算达到 300,000 分且 reserve 为 null 时只展示一次非强制提醒；`reserve=0` 视为用户已经作出设置（D-014）。
7. 预算或必要费用缺项时总体完整性为待核实；只能展示已知小计，不能断言“预算内”。若已知非负费用已超预算，必须展示最低超支额，缺失项不会减少既有支出。
8. 用户自行填写的房费／机票等金额要显示“用户填写，非平台报价”；空金额显示“待核实”，不可通过 D-016 变成已验证供应商报价。
9. 类别只是归类，不产生供应商事实；`estimate`、`demo`、`user_provided` 不得提升为 `verified`。`demo` fixture 只用于测试并始终标记。
10. 重算是纯、幂等操作；重复提交同一快照不重复新增费用。重复 `cost_id` 或同一预订映射多个费用主项时拒绝或返回校验错误，不静默去重金额。
11. 预算模块不编辑锁定预订。费用变更如影响锁定预订，调用方必须由 itinerary 先执行用户主动解锁流程（D-017）。
12. 不自动购买、支付、预订、充值、改变用户预算或调用外部平台（D-012、D-025）。

## 7. 依赖与配置

- **内部依赖：** foundation `MoneyAmount`、`EvidenceState`、`PublicError`、`request_id`；城市／日期不是本模块金额计算的隐式输入。
- **调用模块：** itinerary 组织费用与预订约束；transport/hotels/activities/imports 可提供候选费用，但只有用户确认／来源 contract 允许后才能纳入预算快照。
- **持久化／身份：** 无；后续由 `auth` 和 `local-storage` 提供主体分区和持久保存，需另行 SPEC。
- **外部供应商：** 无。报价来源由各 provider 模块管理；Q-014 的 TTL／限额不由 budget 决定。
- **环境变量：** 无。
- **重试／缓存／限流：** 纯计算无需供应商重试或缓存；API 级请求保护沿用 foundation。实际资源限制在 plan/task 阶段量化并验证，不新增产品上限。
- **测试替身：** 金额 fixture、固定快照、合成唯一 ID、假 request ID；自动化测试禁网。

计划阶段确认具体文件范围，候选结构：


- Python 类型使用 Pydantic strict contract；金额计算集中在纯函数／service，不置于 router。
- 变量与字段用 `snake_case`，类型用 `PascalCase`，常量用 `UPPER_SNAKE_CASE`；错误映射安全且稳定。
- 前端 React + TypeScript，使用生成的 OpenAPI 类型；所有用户金额输入和展示明确元／分转换，未设置值单独呈现。
- UI 语义上分开展示“剩余可安排”和“预计结余”；不得用一种大号总额把定义不同的数字混为一个指标。

示例（金额合计逻辑示意，具体契约须由测试冻结）：

```python
def remaining_to_allocate(total_budget_fen: int | None, paid_total_fen: int | None) -> int | None:
    if total_budget_fen is None or paid_total_fen is None:
        return None
    return total_budget_fen - paid_total_fen
```

## 12. 三层边界

- **Always：** 整趟预算按总额口径；金额以整数分；未知不等于零；已付／待付分开；来源与证据级别保留；预算内结论必须满足完整度；剩余可安排和预计结余分别呈现；用户填写报价明确标记。
- **Ask first：** 改变已确认公式、费用项/人数/预算上下限、货币、预留金规则、持久化／身份边界、引入退款或自动支付、扩展到多城市或供应商报价接入。
- **Never：** 将未知金额当零或免费；重复累计同一预订；把用户填写金额描述为平台报价；自动创建预留金、降低预算、付费或支付；由 budget 模块解锁预订；通过未验证 fixture 声称报价或费用事实已核实。

# SPEC-unknown-ledger：未知项账本

> 状态：范围、计划与任务清单已批准；L2 本地实现完成，发布验收中。用户于 2026-11-16 批准两项首期能力及本文列出的应用内提醒/优先级规则。

## 1. Objective

把旅行数据中所有非 `verified` 的字段聚合为当前 owner 的待核实清单。用户可看到缺少什么、来源状态、影响等级、建议核实时间和返回原模块的入口；系统不把缺项补成 0，也不把用户提供的信息升级为平台核实。

## 2. 范围与数据规则

- 候选项来自已接入 L1 信息护照的天气、班次、地点、预算和行程字段，以及明确标记的未覆盖字段。
- `verified` 以外的 `estimate`、`unverified`、`user_provided`、`unknown` 均可进入账本。`demo` 只在用户明确打开演示数据时出现，不得混入真实工作区。
- 每条候选必须有稳定 ID、对象/字段标签、证据状态、来源/取数时间（若有）、影响等级、建议核实节点及回到所属模块的动作。没有字段级证据的内容不推断成候选。
- 影响等级按序数分类：高（住宿、预约与取消期限）、中（天气覆盖、日程可行性、班次时间）、低（估算票价）；分别建议于 T-7、T-3、T-0 核实。相同节点按高、中、低排序；不计算伪精确分数。
- 到期状态由当前日期和行程出发日纯计算；打开工作区时显示到期/即将到期摘要。页面关闭期间不承诺运行后台定时任务。
- 条目只有在源字段变为 `verified`、对应字段被删除，或旅行被删除时才自动关闭。记录“已联系/待回复”不能伪装成已核实。
- 账本不创建行程事实，不修改天气、班次、POI 或预算值；用户在源模块完成复核后，账本重新计算。

## 3. 生命周期、隐私与依赖

- 账本从当前 owner 的工作区快照派生，不提交新旅行事实到服务器；需持久化的提醒偏好/备注通过现有 IndexedDB owner 分区保存。
- 游客与账号数据隔离；切换 owner 时不得短暂展示上一 owner 的条目。登出保留该 owner 的工作区数据。
- 默认不保存原始订单、OCR 文本、完整查询请求或无必要的金额。账本只存稳定引用与提醒状态；不写 URL、日志或遥测。
- 不新增后端、通知供应商、Push、Service Worker、数据库或依赖。浏览器关闭时的系统通知不属于本版能力。

## 4. UX 与结构

- 在目的地工作区提供账本视图/摘要，沿用现有表单、导航、间距和颜色体系；按旅行日期分组，再按影响和到期时间排序。
- 每条显示字段、当前状态、来源时间、影响级别、下次建议核实日；提供清晰的“前往复核”动作。
- 空状态仅在数据适配器已完成扫描且确无候选时显示“暂无待核实项”；读取失败、字段不可用和空账本必须区分。
- 状态和日期使用可访问文本，不仅依赖颜色；键盘可达，移动宽度无横向溢出。

## 5. Testing Strategy

- 纯函数测试覆盖状态筛选、稳定 ID、字段删除/核实后的关闭、T-7/T-3/T-0 边界、北京时间跨日、影响排序及空值不等于零。
- 集成测试覆盖五类数据适配器、部分缺失/未配置、来源过期、读取失败、owner 切换隔离、登出后恢复和源字段更新。
- E2E 覆盖从账本返回来源模块、复核后条目状态变化、无待核实项、移动端和无障碍语义；只使用合成数据。
- 命令：`npm run test:unit -- --run`、`npm run typecheck`、`npm run lint`、`npm run build`、`npm run test:e2e -- --grep unknown-ledger`。

## 6. Boundaries and Success Criteria

- Always：未核实字段不静默消失；`null` 与 `0` 区分；状态来源可追溯；所有读写遵守 owner 分区；无来源的缺失事实显示未知。
- Ask first：浏览器系统通知、后台提醒、Push/Service Worker、跨设备同步、增加影响类型或权重、跨城市旅行。
- Never：自动把用户提供标成 `verified`；自动补金额/库存/营业时间；在无证据时宣称无待核实项；记录原文件或 OCR 原文。
- 成功条件：所有支持模块的非核实字段均有字段级适配测试；提醒节点按北京时间正确计算；来源模块状态变化后账本一致更新；owner 隔离和登出恢复通过 E2E；原始文件和敏感请求数据不进入账本存储。

## 审批记录

- 用户于 2026-11-16 确认：L2、L6 两项均实施；L2 使用应用内 T-7/T-3/T-0 提示，按高/中/低优先级排序，不做系统通知或后台提醒；对尚未核实的信息保持开放状态。

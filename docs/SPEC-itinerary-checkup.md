# SPEC-itinerary-checkup：行程体检报告

> 状态：已实现并完成本地验收。对应亮点方案 L6 与 Capability Map 模块 `itinerary-checkup`；以当前 owner 的单城市工作区数据做本地、只读分析。用户于 2026-11-16 批准五维体检、缺项显示数据不足、允许添加可选用户填写字段及只读建议边界。

## 1. Objective

出发前对单城市行程给出五维体检、异常项和最多三条按“改动最小、收益最大”排序的建议。数字必须能追溯到当前行程/预算/天气/未知项数据；证据不足时显示“数据不足”，不制造分数。体检本身不得在用户确认前修改安排。

## 2. 五维输入与输出

| 维度 | 手册口径 | 可计算前提 | 数据不足时 |
|---|---|---|---|
| 时间宽松度 | 每日缓冲分钟数 / 计划时长 | 日程含可排序时刻、活动时长、可验证的段间交通时间或用户明确提供的缓冲 | 展示缺少的字段；不把相邻起始时间差直接当通行时间 |
| 预算余量 | (上限 - 计划支出) / 上限，并对待核实金额加权 | 预算上限、已知支出和费用完整性 | 未设置上限、未知金额时标记不完整；不将 null 计为 0 |
| 体力强度 | 步行公里、台阶、换乘、连续户外时长 | 路线段数据与 POI/行程活动标签 | 无路线距离、台阶或活动标签时不打分 |
| 天气风险 | 户外时长 × 对应日降水概率，并叠加极端温度 | 活动日期、室内/户外标签、时长及覆盖该日期的天气结果 | 未覆盖天气或缺少户外/时长信息时标为不完整 |
| 未确认项 | 待核实数量按影响等级加权 | L2 账本的 owner-scoped 候选和已确认的影响规则 | L2 未就绪或权重未配置时不输出综合分 |

每个维度输出 `score: 0..100 | null`、`status`、输入覆盖度、计算说明和引用字段。数据不足时该维 `score=null`；维度充分时显示对应 0–100 分。总报告不把可计算维度的平均值伪装成完整总分；五维全可计算且综合权重经计划审阅冻结后才显示综合分。旧快照没有新增可选字段时保持兼容并按缺失处理。

## 3. Suggestions and mutation boundary

- 只生成可由现有、确定字段支持的规则建议；每条包含受影响日期/安排、理由、预计改善维度和所需数据来源。
- 最多展示三条；信息不足时可以少于三条或为零，不用泛化建议填满列表。
- 未经用户明确确认不得改动行程。被锁定的安排不可由建议直接修改；本版不解锁、不删记录、不创建虚假交通/营业时间事实。
- 建议为只读结果并链接回相关安排；本版不提供“按建议调整”、影响预览或撤销/重做栈，不借 L6 偷渡 L7 可行性引擎或 L12 变更影响预览。

## 4. Lifecycle, privacy, and dependencies

- 报告由当前工作区的 itinerary、budget、weather 和 L2 状态纯计算，不持久化单独评分；页面刷新后根据保存的 owner-scoped 工作区快照重新计算。
- 不把地点、精确路线、金额、天气请求体写入日志/URL；报告与建议只在当前 owner 的工作区内可见。
- 只依赖现有本地数据和已接入 API 响应；不新增 provider、路线请求、POI 标签、模型调用、依赖或后端。
- 依赖顺序：`unknown-ledger` 的字段/权重契约通过后，才冻结未确认项维度；其余维度可独立计算，但报告在所有输入完整前不能声称五维完整。

## 5. UX and structure

- 从行程视图可达“行程体检”，使用现有紧凑工具页风格；优先展示异常项与最有价值的一条建议，再提供五维明细。
- 用可读列表表达五维数值、状态、口径和数据来源；若使用图形，必须有等价文本，不把雷达图作为唯一信息渠道。
- 提供“重新体检”或在输入变化后重算；过期或输入变更时旧结果不可继续显示为当前报告。
- 窄屏下五维不强制横向滚动；色彩不是唯一状态编码；键盘和屏幕阅读器可访问。

## 6. Testing Strategy

- 单测覆盖每维公式边界、负/零/缺值处理、输入来源有效性、天气覆盖缺口、预算完整性、影响权重、确定性排序和最多三条建议。
- 组合测试覆盖五维全部可计算、部分数据、零项行程、单项输入变更导致重算、锁定安排保护和不同 owner 隔离。
- E2E 使用合成行程/预算/天气数据覆盖报告、异常解释、无数据状态、建议确认门和移动端；不调用真实供应商。
- 命令：`npm run test:unit -- --run`、`npm run typecheck`、`npm run lint`、`npm run build`、`npm run test:e2e -- --grep itinerary-checkup`。

## 7. Boundaries and Success Criteria

- Always：每个数字可追溯；缺少数据用 null/不完整状态；同一输入得到确定结果；用户拥有最终修改权；锁定保护和 owner scope 生效。
- Ask first：评分公式/阈值/权重、由体检直接应用建议、route provider 请求、服务端持久化、路线/POI 新数据源和超出一城市的分析。
- Never：从相邻 start time 推断交通时长；把未知预算或天气算成零；在缺失路径/POI 信息时给体力分；自动移动、删除或解锁安排；声称真实通行时间已核实但无来源证据。
- 成功条件：五维输入契约与计算规则获批且有纯函数测试；报告只对有充分输入的维度打分；异常与建议有字段级依据；建议不绕过锁定和用户确认；owner、刷新、响应式、键盘和屏幕阅读器验收通过。

## Open Questions

### 已确认边界与待计划冻结项

- 用户于 2026-11-16 确认：只在数据充分时显示 0–100 分；缺少数据的维度显示“数据不足”；允许增加可选的用户填写字段；建议为只读，不自动改动行程。
- 可选字段：停留分钟、下一段通行分钟、室内/户外/未知、步行公里、台阶数、换乘次数。新字段默认未知并标为 `user_provided`，不调用路线 API；旧快照继续兼容，未填写时对应维度显示“数据不足”。
- 不提供“按建议调整”、影响预览或撤销/重做栈；这些属于 L12/P1。
- 各维度归一化与综合权重须由实施计划提出确定、可解释的规则，并在计划审阅时冻结；不得将亮点方案示例分数当作算法。

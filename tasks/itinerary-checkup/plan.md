# itinerary-checkup 实施计划

> 版本：v0.1｜状态：已实施并验收｜依据：[SPEC-itinerary-checkup](../../docs/SPEC-itinerary-checkup.md) v0.1、已批准首期范围与 Capability Map。

## 1. 目标与边界

在行程视图内只读分析时间宽松度、预算余量、体力负荷、天气风险和未知项五维，显示有据可查的维度分数（0–100）、覆盖状态与异常。建议最多三条，只提供回到编辑入口；不自动改变安排，不集成 L7 路径优化或 L12 影响预览/撤销。

行程安排允许新增可选用户提供字段：停留分钟、下一段通行分钟、室内/户外/未知、步行公里、台阶数、换乘次数。旧快照 schema 向后兼容；空字段为未知而非零。所有用户提供输入标成 `user_provided`，不代表平台验证。

## 2. 数据与计算提案（供计划审阅冻结）

- **时间：** 一日计划跨度以首项开始至末项结束计；总已知活动时间=停留时间合计+用户提供的段间交通时间；可用缓冲=max(0,计划跨度-已知活动时间)。时间宽松度 `score=round(clamp(buffer/plannedDuration/0.30,0,1)*100)`。开始/结束/停留/交通有任何必要字段缺失或计划跨度不大于零时该日为不足；行程分数为充分日的最差值，不跨日平均掩盖最赶的一天。
- **预算余量：** 仅当总预算大于零且预算快照完整、所有必要 paid/unpaid 项均明确时计算。计划支出按现有 Budget API 完整汇总（已付+待付+用户预留）；余量率 `r=(budget-spending)/budget`，`score=round(clamp(r/0.30,0,1)*100)`。未知费用使维度不足，L2 单独表达风险，不把未知金额当零。
- **体力舒适度：** 每日对用户提供数据计算负荷率 `load=max(walk_km/10, stair_steps/100, transfers/8, continuous_outdoor_minutes/480)`，舒适分 `round(clamp(1-load,0,1)*100)`。四项中任一不完整/未知则该日不足；报告给出触发分量，不作医疗/无障碍适配结论。10km、100 级台阶、8 次、8 小时是产品提示刻度，不是健康标准。
- **天气舒适度：** 只使用行程日期被覆盖且 source evidence 为非-demo 的当前天气预报。户外雨险分钟=`outdoor_minutes * precipitation_probability_max_pct/100`；雨险分=`round(clamp(rain_risk_minutes/60,0,1)*100)`。weather_code 为雷暴（95–99）、冻雨（66–67）或强雪（75、86）时风险分 100；温度高于 35℃或低于 -5℃时风险分 100。逐日风险取降水与极端天气风险最大值，舒适分=`100-risk`，行程取最差日。缺室内外标签、时长、天气覆盖、降水概率或温度字段时对应日不足。
- **未确认项：** 使用 L2 高/中/低序数；每项分别扣 20/10/5，`score=max(0,100-Σpenalties)`。读取覆盖不完整时该维不足；过期/已到提醒节点不重复扣分。
- 单项分只在对应输入充分时显示；五维都充分时综合分使用简单算术平均并四舍五入。若任一维不足，不显示综合分。

## 3. 建议排序

只输出数据直接支持的警示：日程重叠/必要字段缺失、最低预算余量、天气高风险日、L2 高影响待办。建议按明确异常优先，其次影响级别，再按旅行日期和稳定 ID 排序，最多三条；不承诺调整后分数，不生成更改方案，不自动重排。具体规则必须用合成输入写纯函数测试并在报告展开理由。

## 4. 实施顺序与检查点

| 顺序 | 工作包 | 验收重点 |
|---:|---|---|
| 1 | 行程可选字段契约/编辑 | 类型、输入上下限与合法性、source/evidence、旧 snapshot 迁移、日期/行程锁保护 |
| 2 | 五维纯计算器 | 每维充分性、分数边界、最差日策略、weather coverage、budget completeness、L2 impact 权重、确定性 |
| 3 | 数据选择器与新视图 | 消费 owner-scoped itinerary/budget、当前 weather、unknown-ledger；状态变化即重算，旧结果不显示 |
| 4 | 建议/异常明细 | 字段级依据、最多三条、锁定安排可见不可变更、回源导航 |
| 5 | 单测、E2E、验收与发布 | 桌面/移动、零项/部分覆盖/全维充分、刷新重算、owner 隔离和无自动 mutation |

App、ItineraryPanel、WorkspaceStore 等共享文件串行改动。L2 必须先完成并验收，才能接入未确认项维度。具体 task 切片每项约不超过五个文件，并先写失败测试。

## 5. 风险与验证

- **现有字段不足：** 多数用户不填写路线/停留/户外字段，因此体检应诚实显示不足，而不是强迫填充或估算。
- **评分解释：** 用户于 2026-11-16 批准上述时间/预算 30% 满分刻度、体力负荷刻度、天气风险阈值、未知项扣分及综合分完整性规则；不将分数包装成客观安全/医学结论。
- **日期天气：** 超出现有 forecast coverage 的行程日必须不足，不使用邻日/历史/演示值补齐。
- **预算数据：** 从 BudgetPanel 使用同一纯计算结果/完整性口径，避免重复维护第二套金额公式。
- 验证命令：`npm run test:unit -- --run`、`npm run typecheck`、`npm run lint`、`npm run build`、`npm run test:e2e -- --grep itinerary-checkup`、Secretlint；整体交付包含后端回归。完成后更新验收记录/Capability Map，独立提交推送 GitHub，并由该提交构建部署服务器，验证 API 健康、前端资源哈希和没有真实供应商副作用。

## 6. 本计划不授权事项

不接入路线/地图 provider、营业时间或预约 API；不自动移动/删除/解锁行程；不实现 L7、L12；不持久化单独体检报告、不改变后端 API、部署 HTTPS、账号或系统通知、不合并 PR。
